# Function Calling隧道方案 - 简化版
## 创建时间：2025年3月16日 11:52 GMT+8
## 创建者：小龙虾 (Xiao Long Xia)

## 1. 项目背景
基于function_Calling文件夹中的"隧道技术"方案，制定简化开发计划。

## 2. 核心思路
**VPN隧道技术**：把Function Call序列化成字符串，藏进消息体里"走私"过去，绕过Monica的过滤。

## 3. 技术方案
### 3.1 数据流
```
OpenClaw → 代理层 → Monica → GPT → 代理层 → OpenClaw
     ↓           ↓         ↓         ↓           ↓
  标准FC     序列化FC   透传消息   返回结果   反序列化FC
```

### 3.2 具体实现
#### 发送时（序列化）：
1. 拦截OpenClaw的tools数组
2. 转换为JSON字符串
3. 用XML标签包裹：`<tools>{...}</tools>`
4. 插入到messages中发送给Monica

#### 接收时（反序列化）：
1. 拦截Monica响应
2. 解析GPT返回的`<tool_call>`标签
3. 转换为OpenClaw标准Function Call格式
4. 返回给OpenClaw执行

## 5. 关键技术点
### 5.1 隐藏格式设计
```xml
<!-- 发送时 -->
<tools>
{"tools": [{"name": "run_command", "description": "执行命令", ...}]}
</tools>

<!-- 返回时 -->
<tool_call>
{"name": "run_command", "arguments": {"cmd": "ls -la"}}
</tool_call>
```

### 5.2 System Prompt设计
```
你拥有调用工具的能力。当需要调用工具时，请严格按以下格式输出：
<tool_call>
{"name": "工具名", "arguments": {...}}
</tool_call>

不要添加任何其他文字。
```

### 5.3 容错处理
1. 正则表达式解析
2. JSON解析异常处理
3. 格式不匹配时的降级策略

## 6. 风险评估
1. **GPT格式不稳定**：通过严格Prompt + 容错解析解决
2. **Monica未来检查**：可升级为Base64等更隐蔽方式
3. **性能影响**：序列化开销极小，可忽略
